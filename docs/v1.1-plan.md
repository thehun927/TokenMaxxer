# tokenmaxxer — shipped LLM extraction behavior and validation

> This document records the shipped behavior that originated as the v1.1 plan.
> It is a behavior reference, not a future implementation checklist.

---

## 0. Scope and policy

Heuristic extraction remains the safe default. LLM extraction is enabled only
when OpenCode starts with:

```bash
TOKENMAXXER_LLM_EXTRACT=1 opencode
```

The environment variable is the feature gate; it is not a model selector.
When the gate is off, tokenmaxxer does not inspect providers, make an LLM call,
or create an extraction session.

The installer also provides `tokenmaxxer opencode [args]`. After installation,
that launcher sets `TOKENMAXXER_LLM_EXTRACT=1` for the child OpenCode process.
It still requires an accessible small model configured through a connected
provider; installation does not supply authentication or entitlement.

### Verified end-to-end result

The shipped flow was verified with connected `ollama-cloud/gpt-oss:20b`:

1. The model returned `StructuredOutput`.
2. tokenmaxxer Zod-validated and merged the extracted facts.
3. `STATE.json` persisted an `llm_extraction_cache` entry.
4. `opencode session list` retained a visible audit session titled
   `tokenmaxxer extract · …`.

The cache entry is keyed by source session, canonical input, and selected
provider/model. The audit session remains visible rather than being deleted.

### Composer and status boundary

Server-side memory work is silent: the idle writer reads and writes project
state and registers pull-based tools without writing to the composer. Automatic
text injection was removed so user-derived or truncated current-task text
cannot surface as a composer message. The server plugin does not use
`experimental.chat.system.transform` for memory and does not require a
generated `HEADER.md` in OpenCode `instructions`.

An optional separate TUI module may expose a fixed right-side memory indicator.
That is a non-composer status surface and lives as a separate TUI plugin target;
it is not part of the server memory transport or a requirement for extraction.

There is no directory-mode memory configuration: resolution uses the OpenCode
`worktree` and falls back to `directory` only when the worktree is unusable.
Vector/search-v2 behavior is likewise not part of the shipped contract.

### Model resolution

Resolution happens from the user's active OpenCode installation, only after a
`session.idle` event has entered the writer path:

1. A syntactically valid top-level `small_model` value in the host config is the
   explicit `provider/model` override. It is passed through exactly as
   configured. The verified example for this environment is
   `ollama-cloud/gpt-oss:20b`; this is not a permanent or universal
   recommendation.
2. If `small_model` is absent or malformed, read the host provider inventory
   from connected providers in `data.all[].models`. Keep only models that are
   active, tool-callable, and reported as zero-cost by model metadata. Prefer
   candidates that advertise an explicit `none` reasoning variant, but do not
   require that variant.
3. Select the first eligible candidate in the host provider-list and model-map
   order, with the `none`-advertising preference above. This is deterministic
   inventory order, not a quality or newness ranking.
4. If the selected model advertises a `none` reasoning variant, request with
   `variant: none`; otherwise request the selected model without forcing that
   unavailable variant.

Provider and model names are never hardcoded. Automatic discovery never falls
back to a paid Anthropic model or any other paid model. An explicit
`small_model` override is the user's direct choice; automatic selection is
always limited to the zero-cost candidates described above.

Structured extraction uses `variant: none` only when the selected model
advertises that variant. The verified explicit `ollama-cloud/gpt-oss:20b`
example has no `none` variant and remains a valid explicit choice. Automatic
discovery does not require `none`, and may select another eligible active,
connected, zero-cost, tool-callable model when no preferred candidate advertises
it. This compatibility policy is operational behavior, not a claim about
permanent model quality or availability.

### Provider credentials and availability

An OpenCode model listing is inventory only. It does not guarantee
authentication, entitlement, thinking/tool-choice compatibility, or adherence
to the structured-result contract. The model must still be accessible through
a connected provider. If a request returns `401`, run:

```bash
opencode auth login
```

Complete the OpenCode/Zen provider flow, then verify the connection with:

```bash
opencode auth list
```

Only connected providers are eligible for automatic discovery. If an explicit
`small_model` is listed but unavailable, not entitled, or not authenticated, its
request fails safe to heuristic extraction rather than being replaced with
another model.

Free offerings change over time, and every provider may have its own data
retention or training policy. Documentation must not promise that any current
free model is permanently available, private, cheapest, or best.

### User configuration

List the providers and models known to the installation. This confirms
inventory only; it does not promise that a listed model is authenticated,
entitled, compatible, or usable without a connected credential:

```bash
opencode models
```

To configure an exact model, copy its IDs into `opencode.json`:

```jsonc
{
  "small_model": "ollama-cloud/gpt-oss:20b"
}
```

The value must be the exact `provider/model` identifier shown by OpenCode. The
Ollama Cloud value is a verified example for this environment, not a promise of
permanent availability, entitlement, compatibility, or quality. Absent or
malformed values intentionally select the discovery path rather than disabling
extraction.

The extraction schema is strict: each `active_files` object requires `path` and
`reason`, and each `decisions` object requires `topic` and `decision`. Prose,
free-form JSON, or code-fenced output is not accepted as a structured result.

### Interactive validation procedure

Do not use `TOKENMAXXER_LLM_EXTRACT=1 opencode run "…"` as an extraction
validation. `opencode run` may exit before the fire-and-forget `session.idle`
handlers complete. It can create the source session while leaving memory
unchanged and without persisting the retained audit extraction session.

Use a fresh source session in the target project instead:

1. Start OpenCode interactively, either directly or through the installed
   launcher:

   ```bash
   TOKENMAXXER_LLM_EXTRACT=1 opencode
   ```

   ```bash
   tokenmaxxer opencode
   ```

2. Send a prompt containing an explicit decision and next step, for example:
   “For an extraction test, explicitly decide to keep the heuristic fallback
   available, state one next step, and do not edit files.”
3. Keep the process open until the source session is idle and its detached idle
   work has completed.
4. Confirm that `.opencode/memory/STATE.json` has a newer timestamp than before
   the test and contains a new `llm_extraction_cache` entry.
5. Run `opencode session list` and confirm that it includes a visible retained
   session titled `tokenmaxxer extract · ...`.

The retained session is an audit record and is never deleted. A cache hit or an
empty discovery result creates no new extraction session; when no eligible
connected model is available, the opt-in path correctly remains heuristics-only.

## 1. Extraction lifecycle

```text
session.idle
  → skip IDs already registered as retained extraction sessions
  → read and cap the source transcript
  → persist heuristic facts first
  → if TOKENMAXXER_LLM_EXTRACT is not "1": stop
  → read small_model and/or inventory OpenCode model metadata
  → if no eligible model: stop with heuristics only
  → build canonical input and cache key
  → on cache hit: merge validated facts; make no session or prompt call
  → on cache miss: create one visible retained extraction session
  → request with variant none only when the selected model advertises it
  → prompt through the host PluginInput v1 client with structured JSON schema output
  → validate the structured result with Zod
  → retry exactly once after a request or validation failure
  → merge validated facts and persist the selected-model cache entry
```

The heuristic write occurs before detached LLM work so a process exit,
configuration problem, unavailable provider, or malformed response cannot lose
the v1 result. A failed LLM attempt returns no replacement facts.

### Canonical input and cache identity

The extraction prompt contains all three components:

- a capped, potentially stale `STATE.json` snapshot;
- a compressed source transcript (text parts only, bounded by message and
  character limits); and
- normalized file candidates derived from source-session tool calls.

The cache key is:

```text
source session ID + SHA-256(canonical input) + provider/model
```

The selected provider/model is part of the identity so changing an explicit
override or changing the discovered candidate cannot reuse facts from another
model. Cache entries contain only validated structured facts and are bounded
with the memory file.

### Prompt and result contract

The prompt asks for current-session facts or deltas, not a copy of prior
memory. The model must report only explicit decisions and evidence from the
source session. The request supplies:

```ts
format: { type: "json_schema", schema: ExtractedFactsJsonSchema }
```

The contract requires `active_files` objects to contain `path` and `reason`,
and `decisions` objects to contain `topic` and `decision`.

Only the structured value returned by the host client is accepted. The result
uses the localized compatibility cast described in §2 and is Zod-validated;
assistant prose, free-form JSON, and code-fence parsing are not fallbacks.

Prompt errors and invalid structured values share one retry budget. The
implementation creates one extraction session, registers its ID before the
first prompt, makes at most two attempts in that session, and retains the
session whether both attempts succeed or fail.

## 2. Host client transport boundary

- Use the host `PluginInput.client` v1 transport for config, provider
  inventory, session creation, transcript access, and structured prompts. Do
  not construct a separate SDK-v2 bridge; a plugin-created bridge cannot reach
  the host server reliably.
- Resolve configuration and inventory only from the `session.idle` writer
  path. Plugin initialization must not call a config or provider API, avoiding
  startup deadlocks.
- Read eligible model candidates from the host provider inventory at
  `data.all[].models`, keeping only active, tool-callable, zero-cost models.
- Do not call `session.delete` for extraction sessions.

The generated v1 client types omit JSON-schema fields that are present in the
existing server responses. Keep this compatibility handling local: use one
cast for the session prompt request and one cast for the session prompt result,
then validate the structured result with Zod. This is a bounded compatibility
risk, not a second transport layer; request or validation failures retry once
and then preserve the heuristic extraction.

The retained-session ID set is an in-process re-entrancy guard. An extraction
session's own `session.idle` event is ignored before dispatching to the writer.
The guard is not persisted across a plugin reload; retained session metadata
still provides the durable audit context.

## 3. Session history and durable memory

Memory schema v2 records `recent_sessions: string[]`, deduplicated and capped
at ten source session IDs. The durable compaction block treats a valid
decision as recent when its `last_used_in_session` is one of the last three
recorded source sessions. Foundational decisions remain in the foundational
tier; older valid decisions are bounded separately and remain queryable with
the recall tools.

The optional LLM cache is stored in the same memory file. A successful
structured extraction upserts a bounded entry. A request failure, invalid
result after the retry, or no eligible connected model writes no cache entry.

## 4. Acceptance checks

### Opt-in and resolution

- No environment variable: no provider inventory, prompt, or audit session.
- Server memory writes are silent and never write project/current-task text to
  the composer; the separate TUI indicator, when installed, is right-side only
  and does not inject composer text.
- `TOKENMAXXER_LLM_EXTRACT=1` plus valid `small_model`: the exact override is
  used.
- Model listings are inventory only: they do not guarantee authentication,
  entitlement, thinking/tool-choice compatibility, or structured-result
  adherence. A `401` requires `opencode auth login`, completion of the provider
  flow, and verification with `opencode auth list` before extraction is enabled.
- Opt-in plus absent or malformed `small_model`: `data.all[].models` from the
  connected-provider inventory is filtered to active, tool-callable zero-cost
  candidates; candidates advertising `none` are preferred, but that variant is
  not required. The first eligible candidate in host provider-list and model-map
  order is used, and `variant: none` is sent only when it exists.
- Discovery uses provider metadata rather than a hardcoded provider/model
  list.
- Automatic discovery selects only connected providers; an explicit unavailable
  model preserves heuristic extraction rather than selecting a replacement.
- No eligible discovery result: heuristic facts remain and no paid fallback or
  audit session is created.
- `opencode models` and the interactive validation procedure are documented
  and usable.

### Extraction correctness

- The source session is written heuristically before LLM work.
- Cache hits make no new session or prompt request.
- A cache miss creates one visible retained audit session and never deletes it.
- The retained ID is registered before the first prompt and its idle event is
  skipped.
- Structured output is read from the host client result and schema-validated.
- Request errors and invalid structured output receive exactly one retry.
- A failed retry preserves the heuristic result.
- The cache key includes source session, canonical-input hash, and selected
  provider/model.
- A verified connected `ollama-cloud/gpt-oss:20b` run returned `StructuredOutput`,
  passed Zod validation, merged facts, persisted `llm_extraction_cache`, and
  retained the `tokenmaxxer extract · …` audit session.
- Existing v1 memory migrates with an empty bounded session-history array.
- Durable recency uses the last three recorded source sessions.

## 5. Risks and operating notes

| Risk | Behavior |
|---|---|
| No eligible model is available | Heuristics only; never silently use a paid model |
| A configured ID is malformed | Use dynamic discovery |
| A provider/model disappears | The request fails safely; heuristic facts remain |
| A listed model lacks a connected credential or entitlement | Authenticate with the host flow; discovery excludes it and explicit use falls back to heuristics |
| Model availability or compatibility changes | Re-inventory from the user's current OpenCode installation and keep heuristics as fallback |
| Provider data policy is unsuitable | The user can disable the feature or choose an explicit model/provider under its terms |
| Generated client types omit server JSON-schema fields | Two localized casts cover the session prompt request/result; Zod validation and one retry fail safe to heuristics |
| Structured output is invalid | One retry, then heuristic fallback |
| Extraction sessions create list noise | Intentional: visible retained audit history |
| Plugin reload loses the guard set | No recursive work is started for newly registered sessions; old metadata remains audit context |
| Detached idle work is interrupted | Atomic memory writes make a missed update preferable to a corrupt file |

No cost estimate or model-quality ranking is permanent: both model pricing and
provider offerings can change.

---

## 6. Operating policy

1. Keep heuristic extraction as the default for every installation.
2. Users who want LLM extraction opt in with
   `TOKENMAXXER_LLM_EXTRACT=1`.
3. Let discovery choose from the current OpenCode inventory unless the user
   supplies an exact `small_model` override.
4. Keep OpenCode open until idle work completes when validating the path, and
   confirm the `STATE.json` cache entry and retained
   `tokenmaxxer extract · ...` audit session.

The shipped policy has no default switch to a named provider or model. The
opt-in gate, exact `provider/model` override, structured contract, and
heuristic fallback remain the operating boundaries.
